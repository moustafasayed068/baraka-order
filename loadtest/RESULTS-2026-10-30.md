# Load test results — 30 Oct 2026

Staging only: local Supabase (Docker, Postgres 17) with the real migrations, 912,500 synthetic past orders, and a
production build of the app (`next start`, one Node process). Everything ran on one 4-core / 15 GB machine together with
k6, so these numbers are **per app instance on shared hardware**, not a prediction for Vercel + hosted Supabase.
Local Kong was lifted to 16,384 connections and Realtime set to Pro-plan quotas (500 connections, 500 events/s) with
`scripts/staging-limits.sh`.

## 1. The current code crashes under sustained load

`publicDb()` and `adminDb()` in `src/lib/db.ts` create a new Supabase client on every call. Each client stays in
memory for good:

| Test | Heap after 20,000 calls |
|---|---|
| new client per call (current code) | 235 MB, growing linearly (~11 KB per client) |
| one shared client | 11 MB, flat |

Under the mixed load the app server reached the 2 GB heap limit and crashed (`JavaScript heap out of memory`) after
about **13,600 requests (~13.5 min)**. Every later request failed (status 0). Order integrity stayed intact.

\* 100-user run had the kitchen simulator bug (kitchens did not move orders); 500/750/1,000 are after the fix.
Each step: 3 min ramp, 3 min hold, ramp down. Plus 10 kitchens, 10 TVs, 10 riders, 5 owner sessions, and open
tracking pages = 50% of customers.

- **Max stable: ~500 concurrent customers per app instance** (p95 270 ms, 0.01% errors). The knee is 500–650.
- **Max sustainable: ~90 req/s mixed traffic** at p95 < 150 ms; hard ceiling ~115–118 req/s (latency then explodes).
- Bottleneck: the single Node process at 100% CPU. Postgres stayed ≤ 45% CPU on customer paths, ≤ 25 connections,
  0 lock waits. When saturated, requests on **new** connections wait ~5 s while warm ones wait ~0.2 s.
- Integrity in every run: 0 duplicate order numbers, 0 gaps, 0 orders without items, 0 wrong totals.

## 4. Database hot spots (owner session through RLS, 912k orders)

| Query | Now | With index + RLS owner short-circuit | |
|---|---:|---:|---|
| Admin orders list, today | 501 ms | 1.1 ms | 450× |
| Dashboard, today | 2,018 ms | 233 ms | 9× |
| Dashboard, 7 days | 3,735 ms | 552 ms | 7× |

Candidate fix (tested inside a rolled-back transaction):
`create index on orders (business_date, created_at desc);` and policies of the form
`using ((select is_owner()) or staff_can(...))` on `orders` and `order_items`.
Under load these two admin reads used ~80% of all database time (5 staff sessions).

## 5. Realtime

- Delivery latency is good: p99 21 ms (100) → 47 ms (500) → 65 ms (1,000).
- Connections: each open tracking page holds one. The Pro cap (500) was hit at 1,000 customers; the Free cap (200)
  would be hit at ~400.
- Broadcast quota: from 500 customers with active kitchens, Realtime dropped thousands of broadcasts
  (`UnableToBroadcastChanges: too_many_requests`). Each status change fans out to every listener at the branch.
  While connected, the tracking page polls only every 30 s, so a dropped "Ready" can arrive up to 30 s late.
